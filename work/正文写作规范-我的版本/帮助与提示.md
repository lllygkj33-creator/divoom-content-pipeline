# 帮助与提示｜正文写作规范

**本栏目正文主线：** 安全或损失边界 → 按症状分流 → 可逆检查 → 恢复验证 → 何时停止、换件或求助。

## 1. 文章承诺

读完必须让用户**恢复**：能按症状分流、做可逆检查、确认是否修好。

## 2. 开头（H1 → 首个 H2：本栏目样本中位 2 段 / 93 词）

本栏目开场**先给判据、再给总览**，不是先讲背景：

1. **第一段必须是可执行判断**——要么给「什么时候立即停用」（安全项优先），要么给「先查什么」的排序。
   范例：`Stop using a baby swing right away if the frame is cracked, bent, leaning, missing hardware, wobbling after tightening, or unable to lock securely.`
2. **第二段给分流总览**：把 H1 里并列的症状拆成互斥的几类，明确告诉读者「先确定你属于哪一类，再往下读」。
3. 本栏目**开头不提产品**（样本品牌提及中位仅 2，五栏最低）——直接进问题，产品留到需要指代结构时才出现。

**本栏目不做：** 不解释不必要的原理、不做同轴决胜、不做购买决策。

## 3. 正文推进（每个 H2 中位 4 段 / 145 词；23 篇里 53 节用列表、仅 5 节用表格）

- H2 就是**症状导航**。每个 H2 必须能独立解决一种故障：用户只读一节就能离开，不被迫读完全篇。
- 节内顺序固定：**先安全界限 → 再最常见原因 → 最后罕见原因与升级**。
- 本栏目靠**列表**承载分支（53 节），**几乎不用表格**（5 节，五栏最低）。分支应该由 H2 + 清单表达；把故障摊进表格会让「我该做哪一步」变模糊。
- 每节收尾给一个**验收结果**：做完这一步应该观察到什么（「盖子合上后接缝处不再有气味」），而不是「这样就修好了」。
- 一次只让用户做一步，且每步可逆。不要给一次性完整拆机流程，也不要写「原因一／原因二」这种序号式罗列。

## 4. 证据与产品提及

- 可核查的**结构事实**查 `../../实体库/实体变量库.csv` 的 `部件`(51) / `接口与依赖`(27) / `状态与症状`(12)：有哪些部件、什么接口、供电与充电状态、播放与开关状态。
- **安全项必须先给停止使用界限**：涉及电气与电池、安装与坠落、防水与进水、儿童与麦克风／隐私时，先写「什么情况下不要继续用」，再写怎么处理。缺边界说明会被机械封顶压到 5.5。
- **配件是否随附、可否单独购买一律写「以商品页为准」**，不臆测、不给购买链接。
- 产品提及只在「这个故障出现在哪一类产品结构上」时出现一次，**不写型号名**（硬伤）。
- 范文里的医疗建议、竞品故障率、竞品链接一律不得进稿。

## 5. 栏目专属结尾

给**恢复／升级条件**：说明什么状态算已恢复，什么情况下应停止自行处理、换件或求助。

## 6. 链接与审核

先完成正文，再按本栏目 `锚文本规范.md` 与 `../发布与链接记录/` 两张台账补链；逐条检查链接是否真的回答了锚文本所指的子问题。
