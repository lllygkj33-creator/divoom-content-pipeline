# Technology Hub：案例绑定、段落推进与图文共同规划

Technology 新稿在大纲阶段读取本文件和 [已核对案例索引](technology-cases.json)。源规范的 FX 映射仍有效；本文件覆盖把统计中位数当作固定写作模板的做法。原始快照不改写。

## 1. 先绑定同 FX 案例

从原 FX 主表找到本题对应的案例 URL，读取该页正文与正文图片，再规划自己的大纲。不要沿用最近一次主题排版讨论、搜索结果排名或同品牌的另一篇文章。字体/布局样本与标题/论证样本分开记录。

在 `outline.json` 写 `editorial_protocol_version: 2` 和 `sample_review`：

- `fx`、`url`、`status`（read / snapshot_only / unavailable）、`checked_at`。
- `adopt`：要迁移的推理或呈现方式；`avoid`：不能照搬的部分；`reason`：为什么与本标题相配。
- `visual_inspection`：pixels / metadata_only / none。仅看 alt、文件名不能记为 pixels，也不能声称看过图片。

read 必须有本次实际读取时间。无法读取时说明原因，用可信快照继续结构规划，并保留未实时核实状态；没有关键事实证据仍按 evidence 门禁阻止导出。案例提供结构，不是 Divoom 产品事实。

F14 原始截图的标题/URL 仍未核实。索引中的乳房按摩文章只作新找到的补充候选，不能称找回原样本、不能自动把 F14 改成已验证范式。候选使用时保留这一说明。

## 2. 从“下一问”组织段落

每节先写独立问题和新增信息，再决定用几个段落。3–5 段、某个词数范围是旧样本观察，不是配额。相邻小节段数一样不自动扣分，段数不一样也不自动加分。

选择所需职责：直接答案、机制解释、条件改变、可观察对照、反例、适用边界、承接下一问。一个段落可以完成相邻的两个职责；不要要求每节依次完成同一套四步。只删去真正重复的结论，不为了“节奏变化”把连贯因果链切碎。

每个 section 增加 `format`（prose / list / table / mixed）、`format_reason` 和 `transition`。transition 说明上节留下了什么问题、本节为什么接在这里；末节说明收束什么。并列变量适合列表，同轴条件对照适合表格，先后依赖才用编号。列表/表格附近必须有解释如何判断的文字；不要为形式指标把全部正文改成清单。

## 3. 小条件与多场景必须改变判断

在 `scenario_plan` 记录 `needed`、`reason`、`cases`。每个 case 含 `section`、`condition`、`changes`、`stays_constant`、`reader_signal` 和 `claim_ids`。

先固定比较对象与观察目标，再改变一个有解释力的条件。例如：同一音箱在正常与更高播放音量下的低音相对平衡；相同播放设置下，靠墙和远离边界的观察。每个场景明确什么改变、什么不变、读者应观察什么。场景不是虚构的测试结果，不给没有测得的 dB、阈值或型号结论。

若“办公桌、卧室、旅行”只是换地点，结论不变，就合并。条件确实不影响本题时允许 cases 为空，写明理由；不要求每篇固定两个或三个场景。反例若改变结论，应放在相应主张附近，不能只放在末尾免责声明中。

## 4. 写之前规划图位

正文配图承担一个具体子问题：机制图、条件对照、部件映射、读数示例、过程图或真实场景。图片不是装饰配额，也不是事实证据。不能从页面成品反推竞品一定先画图后写作，不能从画风或文件名断言其自动化工具。

`visual_plan` 为数组；无必要配图时可为空，同时写非空 `visual_reason`。每项含：

- `id`、`role`（banner / explanatory / comparison / scene / measurement / process）、`section`（banner / intro / 实际 section id）、`after_paragraph`（从 0 起，解释计划位置）。
- `purpose`：具体帮助理解哪一句；`claim_ids`：图内涉及事实的证据索引，可为空表示纯布局/情境示意。
- `asset_status`：pending / ready / omitted；`src`：只有 ready 才填已核实真实 URL，其余为空。

优先把图放在读者已知道要看什么之后、需要空间/流程/对照理解的位置。2026-10-17 的 13 篇对应样本中，43 张正文图有 41 张位于所在小节前三个实质段落内；这是观察结果，不是“每三段一图”或“每 H2 一图”的规定。图片后可用一句话解释该看哪个差异；不重复图上全部文字。

封面服务栏目卡片；banner 服务文章页顶部；正文图服务具体论证。三者分别规划。当前模板从正文最前面的独占图片段提取 banner；只有真实 banner 已就绪时才将其置于两个实质开头段之前。封面不自动塞进正文，含整篇标题的封面也不自动当标题背景。

无素材时仍完成图位规划。internal 模式不向 HTML 输出素材要求；本部署配置的 html_comments_v1 模式按 [配图交付契约](image-prompt-handoff.md) 将完整英文 prompt 作为保留注释放在原图位。两种模式均不创建 pending img、假 URL 或可见占位文字。正文必须独立可理解；必要的信息先用文字或可核实表格呈现。不自动调用生图、上传或发布。

## 5. 图片事实与可读性

- 实际查看像素，再核对 URL、alt、正文论点和图中内容。alt 描述画面，不增加画面无法证明的实验条件或身份。
- 数值、单位、阈值、坐标、年代和比较标签必须对应 evidence。生成的示意曲线不能冒充实测，现代产品照片不能证明历史外观。示意图应明确其示意身份。
- 型号外观、接口、UI 与内部构造使用适用的官方或用户素材；不能让生成器发明 Divoom 硬件或设置界面。
- 图中标签少而必要，移动端可读；核对编号、箭头、图例、单位和拼字。精确图表与文字优先用可校验的图形/排版工具完成，而不是依赖生成图片中的小字。
- 品牌强调使用 #FE9210；参考的是解释功能，不复制 Momcozy 图片、粉色视觉或医学主张。健康、安全及版权相关内容仍需独立核实。

## 6. FAQ 是决定，不是默认模块

`faq_decision` 含 `include`、`reason`、`questions`。只为主体尚未回答、与标题紧密相关的真实疑问保留问答。没有增量则 include=false、questions=[]。当前对应样本中 6/13 有独立 FAQ，F1 没有；两者都不能变成所有文章的硬规则。

## 7. 最小内部契约

以上完整审核记录留在 outline，不进入用户 JSON 顶层；选定交付模式的待配图 prompt 仅以正文保留注释随稿。新建 Technology run 采用协议 2；历史 run 保持旧格式可读。正文、素材、FAQ、prompt 或条件发生实质改变，更新计划和证据并重新封存；链接阶段不能绕过这一过程。

最终复核按 [编辑审核](editorial-review.md) 在 review 中登记。机械脚本只检查计划完整、案例映射和素材状态；不会判断段落优美、场景有效或图片真实。
