# Divoom 内容流水线｜Skills 撰写需求文档

**用途**：把本文档整份丢给 GPT，让它按结构产出 5 份 `SKILL.md`。
**交付物**：5 个文件，逐个对应一个角色。写完后放回指定路径即可。

---

## 一、总背景（先读这段，其余都建立在这上面）

这是一条 **Divoom 品牌内容生产流水线**，用 DSH（DeepSeek Harness）的可视化多 Agent 编排执行。每个角色是一个独立的子 Agent，有自己的 system prompt（就是你要写的 skill）和独立的工具权限。

**内容站点**：divoom.com（英文站，卖像素艺术音箱、像素显示屏、蓝牙音箱、卡拉OK设备、LED 背包、充电器）。
**成稿语言**：英文。Skill 正文用中文写（给 Agent 读的指令），产出的文章内容是英文。
**知识库**：一个 Obsidian 资料库，Agent 通过文件路径读取。

**流水线链路**：

```
用户给一个主题
  ↓
① brief官      检索实体库 + 真实搜索需求 → 产出 brief（含润色标题、栏目、FX 编号、大纲逻辑、参考 URL）
  ↓
② 内容编辑     按 brief 写 H1 + 大纲 + 正文 + HTML
  ↓
③ 审核官       对照实例正文多维打分 → 达标放行 / 不达标打回 ②（最多 2 轮）
  ↓
④ SEO优化师    补齐 meta title / description / summary / 锚文本 / 内链 / 外链
  ↓
⑤ GEO优化师    按 query fan-out 判断缺口 → 补 FAQ 问答 或 收尾段落
  ↓
final.json + final.html
```

---

## 二、交付格式要求（必须严格遵守）

每份 skill 是一个 Markdown 文件，**必须有 YAML frontmatter**：

```markdown
---
name: <英文小写连字符名，全局唯一>
description: <一句话，说清这个角色做什么、什么时候用；这是 Agent 决定是否加载的依据，要具体>
---

# <中文角色名>作业手册

（正文）
```

**正文结构统一为这五节**（顺序固定，标题可用更适合该角色的措辞）：

1. **你是谁 / 你的边界** —— 用第二人称写（"你是……"），明确写出**只做什么、绝不碰什么**
2. **先读什么** —— 按顺序列出要读的文件路径与读它的目的
3. **怎么做** —— 分步骤的执行流程，越具体越好
4. **输出格式** —— 精确到字段名、文件名、写到哪个目录
5. **交付前自检** —— 用 `- [ ]` 复选框列出自检项

**硬性写作要求**：

- **每份控制在 6000 字符以内**（编排层给文件节点的注入上限是 20000 字符，留足余量）。超了会被截断。
- **不要复制粘贴知识库里的规范原文**（锚文本类型表、正文写作规范等）。那些文件 Agent 自己会去读，skill 里只写"去读哪个文件、用它的哪一部分、怎么用"。规范会独立演进，抄进 skill 必然分叉。
- **不要复制竞品实例全文**（74 篇，76 万字符）。实例留在知识库里检索，skill 只写"去哪读、怎么用"。
- **规则要可执行、可判定**。"注意质量""保持自然"这类不可判定的要求不要写。要写成"锚文本 3–6 词""FAQ 每条 40–90 词"这种能验证的。
- **把硬约束写死在 skill 里**，不要让 Agent 自己权衡。本文档第四节列出的硬约束，各角色相关的必须原样出现在 skill 中。

## 四、硬约束（各角色相关部分必须原样写进 skill）

1. **内链只能指向 `发布与链接记录/已发布文章.md` 里真实存在、已发布、可访问的 Divoom URL。** 台账里没有合适目标就登记到 `待补内链.md`，**正文里绝不留空链接、占位符或编造的 URL**。
2. **所有 Divoom 事实只能来自 `实体库/`。** 实体库 `产品型号` 组**是空的（有意为之）**，所以**不得编造型号名**；要指代产品时用实体库里的品类或部件词。
3. **竞品实例（Momcozy/KTC）只作结构参考。** 其产品事实、医疗建议、具体数据、目标链接**不得**写进 Divoom 成稿。
4. **字段只增不减**：后一角色只补自己拥有的字段，不得清空前序字段。
5. **回环不覆盖历史**：编辑每被打回一次就出新版本文件（`v2`、`v3`），审核同理。
6. **审核官不改稿**（只出意见与分数）；**GEO 优化师不改正文**（只判断与补 FAQ）。

## 五、JSON 字段契约（各角色只拥有下表中属于自己那一列）

**字段只增不减。最终 JSON 固定 20 个字段，不增不减。**

| 字段 | 归属角色 | 说明 |
| --- | --- | --- |
| `topic` | ① | 用户原始主题 |
| `column` | ① | 栏目中文名 |
| `fx` | ① | FX 编号（如 `BG1`） |
| `h1` | ② | 正文 H1 |
| `title` | ④ | meta title，50–60 字符 |
| `meta_description` | ④ | 140–160 字符 |
| `summary` | ④ | 60–90 词 |
| `slug` | ④ | 从 H1 生成的小写连字符 slug |
| `url` | — | **留空**，发布时由人回填 |
| `body_markdown` | ② 产出、④ 仅插入链接 | SEO 优化后的完整正文 |
| `html` | ② 产出正文 HTML、⑤ 追加 FAQ | 只给正文片段，不含 `<html>`/`<head>` |
| `faq` | ⑤ | `[{question, answer}]` |
| `closing_paragraph` | ⑤ | 无 FAQ 时的收尾段 |
| `internal_links` | ④ | `[{anchor, url, h2, type}]` |
| `external_links` | ④ | `[{anchor, url, why}]` |
| `pending_links` | ④ | `[{anchor_candidate, topic, h2, reason}]` |
| `fanout` | ⑤ | `[{layer, question, verdict, evidence}]`，layer ∈ 定义/条件/对比/操作/边界/成本，verdict ∈ covered/gap_filled/out_of_scope |
| `eeat_notes` | ⑤ | 字符串数组，观察而非改写 |
| `review` | ③ | `{scores, verdict, rounds, revision_notes}`，verdict ∈ pass/revise/escalate |
| `generated_at` | 汇总 | ISO 时间戳 |

**另外，① 的 brief 有自己独立的字段**（写进 `00-brief.json`，不进最终 JSON）：
`topic`、`column`、`fx`、`polished_title`、`search_demand`、`outline_logic`、`reference_urls`。

## 七、五份 skill 各自的要点

### ① brief官

- **目标**：拿到用户主题，产出一份可直接交给编辑的 brief。
- **必做**：从主题里抽出对象/条件/现象/结果等槽位 → 查 `实体库/` 确认这些概念在 Divoom 语境里成立 → 查**外部真实搜索需求**（说明清楚用什么方式获取，让 Agent 可执行）→ 润色标题 → 用第三节的路由规则定栏目 → 从该栏目 `标题与大纲规范.md` 的 FX 主表选**一个**最匹配的 FX → 给大纲逻辑链路（按该 FX 的 H2 箭头逻辑，结合本主题的限定词调整）→ 给参考 URL 清单。
- **边界**：不写正文、不选锚文本、不写 meta。
- **关键要求**：标题必须保留原主题的限定词（`after`、`even when`、`without`、`vs`、`for [role]`）；FX 只能选一个；参考 URL 必须真实可访问。
- **产出**：`00-brief.json`。
- **待你补充**：**外部真实搜索需求从哪里获取**（关键词工具？搜索联想？站内搜索？）。这一项写不清 Agent 就会瞎编。

### ② 内容编辑

- **目标**：按 brief 写出第一轮正文。
- **必做**：读 brief → 读本栏目 `标题与大纲规范.md`（确认 FX 的 H1 公式与 H2 箭头）→ 读 `正文写作规范.md` → 用实体库事实写正文 → 产出 H1 + body_markdown + html。
- **必读规范**：`正文写作规范.md` 里的「文章承诺／开头／正文推进／证据与产品提及／栏目专属结尾」五节，按栏目分别执行。
- **边界**：**此轮不产出** `title`/`meta_description`/`summary`/`slug`/`url`/`faq`/内链/外链。写了也会被后续角色覆盖。
- **关键要求**：H2 按 FX 的箭头顺序推进，不写 H3；正文 1200–2200 词；开头两段直接回应 H1、不先推产品；每个 Divoom 事实都能在实体库查到。
- **产出**：`01-draft-v1.json`。

### ③ 审核官

- **目标**：对照本栏目实例正文，多维打分，决定放行或打回。
- **必做**：读编辑稿 → 读本栏目 `实例汇总.md`（或按需读 `实例/` 下单篇）建立质量基线 → 按维度打分 → 给**可执行的修改意见**（指明哪一段、缺什么、怎么改）→ 出 verdict。
- **建议评分维度**（可调整，但要有明确分值区间）：`eeat_experience`、`eeat_expertise`、`eeat_authoritativeness`、`eeat_trust`、`hcu_helpfulness`、`ymyl_risk`、`fact_grounding`，每项 0–10。
- **特别要求**：`fact_grounding` 要逐条核正文里的 Divoom 事实是否都能在 `实体库/` 查到 —— **查不到就是硬伤**。
- **边界**：**不改稿**，只出意见与分数。
- **产出**：`02-review-v1.json`（对应版本号）。
- **待你补充**：**放行分数**（如 80/100）与**维度权重**。可以先留占位。

### ④ SEO优化师

- **目标**：在已过审的正文上补齐 SEO 字段。
- **必做**：读 `锚文本总规范.md`（16 类定义 + 词数标准）→ 读本栏目 `锚文本规范.md`（类型表 + 选链规则）→ 读 `发布与链接记录/已发布文章.md` 找真实内链目标 → 在正文里就地插入链接 → 写 meta 三件套 → 生成 slug。
- **边界**：不改正文观点、H2、段落结构；不编造链接；不做 FAQ。
- **关键要求**：`internal_links` 必须与 `body_markdown` 里实际出现的链接**一一对应，不多不少**；`pending_links` 里的条目**不得**出现在正文中。
- **产出**：`03-seo.json`。

### ⑤ GEO优化师

- **目标**：按 query fan-out 判断内容缺口，补 FAQ 或给收尾段落。
- **必做**：读 SEO 稿 → 读本栏目 `实例汇总.md` 学 FAQ 深度与问法 → 读 `标题与大纲规范.md` 确认 H1 承诺 → 按六层拆 fan-out 子问题（定义/条件/对比/操作/边界/成本）→ 逐条判定 covered/gap_filled/out_of_scope → 写 FAQ 或收尾段。
- **边界**：**不改正文一个字**；FAQ 里不得出现竞品事实；涉及 Divoom 事实必须能在实体库查到。
- **关键要求**：`faq` 与 `closing_paragraph` **互斥**（有缺口给 FAQ，没缺口给收尾段）；FAQ 每条 40–90 词、第一句直接答、可独立读懂；没有真实缺口时**宁可给收尾段，不要硬造问题**。
- **产出**：`04-geo.json`。
